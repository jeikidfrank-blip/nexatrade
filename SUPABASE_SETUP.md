# Supabase backend setup

NexaTrade uses Supabase for authentication, account balances, transaction history, and server-side simulated trade execution. The browser uses the project's URL and publishable key plus the public Web Push key from `supabase-config.js`; never put a Supabase service-role key or VAPID private key in the site.

## Set up the database

In the Supabase project configured in `supabase-config.js`, open **SQL Editor** and run these files in order:

1. `supabase-demo-accounts.sql`
2. `supabase-real-test-account.sql`
3. `supabase-real-test-trading.sql`
4. `supabase-internal-transfers.sql`
5. `supabase-withdrawal-messages-vip.sql`

The scripts create the tables, row-level security policies, signup triggers, and RPC functions used by `app.js` and the Messages inbox. They are intended to be rerunnable. The trading script updates prices and relevant account functions to use KSh. The internal-transfer migration adds a server-validated transfer RPC and ledger entries; run it before using the Internal transfer menu. Before sending, the app verifies that the recipient username or phone number belongs to an existing NexaTrade account with a simulated account, then asks you to confirm. The withdrawal-messages migration also creates the per-device push subscription table.

## Enable withdrawal phone notifications

Web Push needs a VAPID key pair, one Edge Function, and a database webhook. Keep the VAPID private key and webhook secret out of browser code and Git.

1. Generate a VAPID key pair in a terminal with `npx --yes web-push generate-vapid-keys`.
2. Put the generated **public** key in `supabase-config.js` as `webPushPublicKey`. Do not put the private key there.
3. In the Supabase project directory, set the Edge Function secrets and deploy the push handler:

   ```powershell
   supabase secrets set VAPID_PUBLIC_KEY="<generated-public-key>" VAPID_PRIVATE_KEY="<generated-private-key>" VAPID_SUBJECT="mailto:<your-email>" WITHDRAWAL_PUSH_WEBHOOK_SECRET="<a-long-random-secret>" --remote=<project-ref>
   supabase functions deploy withdrawal-push --no-verify-jwt --remote=<project-ref>
   ```

   Use the same long random value for the database webhook's `x-webhook-secret` header.
4. In Supabase Dashboard, open **Database > Webhooks** and create a webhook for `public.nexatrade_withdrawal_messages`, on **INSERT** only. Set its URL to `https://<project-ref>.supabase.co/functions/v1/withdrawal-push`, method to **POST**, and add the `x-webhook-secret` header with the secret from step 3.
5. Deploy the site over HTTPS. On the phone, install Messages as a PWA, sign in, open the account menu, and tap **Enable phone notifications**. Accept the browser's permission prompt.
6. With the Messages page closed, create a simulated withdrawal. The phone should show a system notification; tapping it should open the MPESA conversation.

On iPhone/iPad, Web Push requires iOS/iPadOS 16.4 or later and the site added to the Home Screen. Android users should install the site from a supported browser for the most reliable background delivery.

The current withdrawal inbox message is generated by NexaTrade's simulated withdrawal flow. These notifications alert on that database message; they do not read carrier SMS messages or indicate that a real M-Pesa transfer occurred.

## Configure authentication

In Supabase, open **Authentication > URL Configuration** and set the site's deployed URL and any local development URL as allowed redirect URLs. Configure email-confirmation behavior under **Authentication > Providers > Email**.

## Verify the backend

1. Open the site and create a test user.
2. Confirm signup and sign in.
3. Check that the Demo and Test Funds tabs load balances.
4. Try a simulated deposit/withdrawal and a demo trade.
5. Create or use a second signed-up account, send it a small simulated internal transfer by username or sign-up phone number, and confirm the sender and recipient transaction histories and balances update.
6. In Supabase **Table Editor**, verify that each account's transactions are scoped to that user and the transfer ledger records match.

The Test Funds account is simulated: this setup does not connect a payment provider or execute live trades. Do not use it to accept real deposits.
